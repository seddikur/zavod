Документ: Структура БД учёта материалов бетонного завода
1. Назначение и область
   Система ведёт учёт материалов (щебень, цемент, вода, добавки) на бетонном заводе: приход от поставщиков, расход по рецептам при отгрузке бетона покупателям, текущие остатки по складам. Ключевой принцип — журнал движений (append-only) является источником истины, таблица остатков — производный агрегат, обновляемый инкрементально в той же транзакции.

Принятые архитектурные решения:

Одна таблица materials на все материалы (не отдельная таблица под каждый) — материалы различаются данными, а не структурой.

Движения хранятся в отдельных таблицах-журналах (приход / расход / корректировка), не удаляются — отмена только сторно-документом.

material_stock обновляется инкрементально (± quantity) при проведении документа в одной транзакции. Это паттерн Event Sourcing + Snapshot / CQRS Read Model, в ERP-терминологии — агрегатная таблица остатков (аналог SAP MARD).

Все количества хранятся в базовой единице измерения (кг или т — выбрать одну и зафиксировать), unit_id — для отображения.

8. Методы записи, удаления и смены статуса
   8.1. Приход — создание (draft)
   sql
   BEGIN;
   INSERT INTO receipts (doc_number, doc_date, supplier_id, warehouse_id,
   status, created_by)
   VALUES ('ПН-001', :date, :supplier, :wh, 'draft', :user)
   RETURNING id;  -- :receipt_id

INSERT INTO receipt_items (receipt_id, material_id, quantity, unit_id, price, amount)
VALUES (:receipt_id, :mat, :qty_base, :unit, :price, :qty_base * :price);
-- остаток НЕ трогаем: документ ещё draft
COMMIT;
8.2. Приход — проведение (draft → posted)
sql
BEGIN;

-- 1. проверка статуса
SELECT status FROM receipts WHERE id = :receipt_id FOR UPDATE;
-- если status <> 'draft' → RAISE EXCEPTION

-- 2. для каждой строки прихода — upsert остатка
INSERT INTO material_stock (material_id, warehouse_id, quantity)
SELECT ri.material_id, r.warehouse_id, ri.quantity
FROM receipt_items ri
JOIN receipts r ON r.id = ri.receipt_id
WHERE ri.receipt_id = :receipt_id
ON CONFLICT (material_id, warehouse_id)
DO UPDATE SET quantity = material_stock.quantity + EXCLUDED.quantity,
updated_at = now();

-- 3. статус
UPDATE receipts SET status = 'posted', posted_at = now() WHERE id = :receipt_id;

COMMIT;
Если любой шаг упал — откат всего. rows_affected у upsert проверять не нужно (upsert всегда затронет строку), но для обычного UPDATE — обязательно.

8.3. Отгрузка — проведение (draft → posted)
sql
BEGIN;

SELECT status, recipe_id, actual_quantity, warehouse_id
FROM production_orders WHERE id = :order_id FOR UPDATE;
-- если status <> 'draft' → RAISE EXCEPTION

-- 1. рассчитать и вставить строки списания из рецепта
INSERT INTO production_consumptions
(production_order_id, material_id, recipe_item_id, quantity, unit_id)
SELECT :order_id,
ri.material_id,
ri.id,
ri.quantity * (po.actual_quantity / r.output_quantity),
ri.unit_id
FROM production_orders po
JOIN recipes r        ON r.id = po.recipe_id
JOIN recipe_items ri  ON ri.recipe_id = r.id
WHERE po.id = :order_id;

-- 2. блокировка и проверка остатка (для каждого материала)
SELECT quantity FROM material_stock
WHERE material_id = :mat AND warehouse_id = :wh
FOR UPDATE;
-- если quantity - :consume_qty < 0 → RAISE EXCEPTION (или разрешить по политике)

-- 3. списание остатка
UPDATE material_stock
SET quantity = quantity - :consume_qty, updated_at = now()
WHERE material_id = :mat AND warehouse_id = :wh;

-- 4. статус
UPDATE production_orders SET status = 'posted', posted_at = now()
WHERE id = :order_id;

COMMIT;
8.4. Отмена проведённого прихода — сторно (posted → reversed)
sql
BEGIN;

SELECT status, warehouse_id FROM receipts WHERE id = :receipt_id FOR UPDATE;
-- если status <> 'posted' → RAISE EXCEPTION

-- 1. сторно-шапка
INSERT INTO receipts (doc_number, doc_date, supplier_id, warehouse_id,
status, reversal_of, reversal_reason, created_by)
SELECT doc_number || '-СТОРНО', CURRENT_DATE, supplier_id, warehouse_id,
'draft', id, :reason, :user
FROM receipts WHERE id = :receipt_id
RETURNING id;  -- :storno_id

-- 2. сторно-строки с минусом
INSERT INTO receipt_items (receipt_id, material_id, quantity, unit_id, price, amount)
SELECT :storno_id, material_id, -quantity, unit_id, price, -amount
FROM receipt_items WHERE receipt_id = :receipt_id;

-- 3. провести сторно (как в 8.2, но quantity уже отрицательный)
--    upsert остатка с EXCLUDED.quantity (минус) → вычитание
INSERT INTO material_stock (material_id, warehouse_id, quantity)
SELECT ri.material_id, r.warehouse_id, ri.quantity
FROM receipt_items ri JOIN receipts r ON r.id = ri.receipt_id
WHERE ri.receipt_id = :storno_id
ON CONFLICT (material_id, warehouse_id)
DO UPDATE SET quantity = material_stock.quantity + EXCLUDED.quantity,
updated_at = now();

-- 4. статусы
UPDATE receipts SET status = 'posted', posted_at = now() WHERE id = :storno_id;
UPDATE receipts SET status = 'reversed', reversed_by = :storno_id WHERE id = :receipt_id;

COMMIT;
Сторно отгрузки — аналогично, через production_orders + production_consumptions с минусом.

8.5. Удаление
Что	Разрешено?	Как
receipts / production_orders в статусе draft	Да	DELETE (остаток не затронут)
receipts / production_orders в статусе posted	Нет	Только сторно (8.4)
receipt_items / production_consumptions	Нет (триггер)	Только через сторно-документ
adjustments в статусе draft	Да	DELETE
adjustments в статусе posted	Нет	Компенсирующий adjustment
materials, recipes, customers, suppliers	Только is_active = false	ON DELETE RESTRICT из движений
Триггер-запрет на удаление движений:

sql
CREATE OR REPLACE FUNCTION forbid_delete() RETURNS trigger AS $$
BEGIN
RAISE EXCEPTION 'Deleting movements is forbidden. Use reversal document.';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_no_delete_receipt_items
BEFORE DELETE ON receipt_items
FOR EACH ROW EXECUTE FUNCTION forbid_delete();

CREATE TRIGGER trg_no_delete_production_consumptions
BEFORE DELETE ON production_consumptions
FOR EACH ROW EXECUTE FUNCTION forbid_delete();
8.6. Смена статуса — сводная матрица
Документ	Из	В	Условие	Действие с остатком
receipts	draft	posted	есть строки	+ quantity upsert
receipts	posted	reversed	создан сторно	− quantity (через сторно-документ)
production_orders	draft	posted	есть рецепт, расчёт выполнен	− quantity upsert
production_orders	posted	reversed	создан сторно	+ quantity (через сторно-документ)
adjustments	draft	posted	есть строки	± quantity upsert
Запрещённые переходы: posted → draft, reversed → posted, reversed → draft. Статус reversed — финальный.

9. Механизмы контроля целостности
   9.1. Транзакционность (уровень 1)
   Движение + UPDATE material_stock — в одном BEGIN/COMMIT. При сбое откатывается всё. Для UPDATE проверять rows_affected = 1, иначе RAISE EXCEPTION. Для остатка использовать upsert (ON CONFLICT DO UPDATE), чтобы не зависеть от заранее созданной строки.

9.2. Блокировки (уровень 1)
При списании — SELECT ... FOR UPDATE строки material_stock перед проверкой остатка и UPDATE. Порядок блокировок — сортировка по (material_id, warehouse_id), чтобы избежать дедлоков при многоматериальных отгрузках.

9.3. Запрет DELETE (уровень 1)
Триггеры на receipt_items, production_consumptions, adjustment_items. Отмена — только сторно.

9.4. Сверка «остаток ↔ журнал» (уровень 2)
sql
SELECT s.material_id, s.warehouse_id,
s.quantity AS stock_qty,
COALESCE(r.qty,0) - COALESCE(c.qty,0) + COALESCE(a.qty,0) AS ledger_qty,
s.quantity - (COALESCE(r.qty,0) - COALESCE(c.qty,0) + COALESCE(a.qty,0)) AS diff
FROM material_stock s
LEFT JOIN (SELECT ri.material_id, r.warehouse_id, SUM(ri.quantity) qty
FROM receipt_items ri JOIN receipts r ON r.id = ri.receipt_id
WHERE r.status IN ('posted','reversed')
GROUP BY ri.material_id, r.warehouse_id) r
ON r.material_id = s.material_id AND r.warehouse_id = s.warehouse_id
LEFT JOIN (SELECT pc.material_id, po.warehouse_id, SUM(pc.quantity) qty
FROM production_consumptions pc JOIN production_orders po ON po.id = pc.production_order_id
WHERE po.status IN ('posted','reversed')
GROUP BY pc.material_id, po.warehouse_id) c
ON c.material_id = s.material_id AND c.warehouse_id = s.warehouse_id
LEFT JOIN (SELECT ai.material_id, a.warehouse_id, SUM(ai.quantity) qty
FROM adjustment_items ai JOIN adjustments a ON a.id = ai.adjustment_id
WHERE a.status = 'posted'
GROUP BY ai.material_id, a.warehouse_id) a
ON a.material_id = s.material_id AND a.warehouse_id = s.warehouse_id
WHERE s.quantity <> (COALESCE(r.qty,0) - COALESCE(c.qty,0) + COALESCE(a.qty,0));
Учитываем status IN ('posted','reversed'): сторно-документ имеет posted и минусовые строки, исходный — reversed и плюсовые. Оба попадают в журнал, сумма = 0. Запускать по расписанию (ночью) или по кнопке «Сверка».

9.5. Сверка «документ ↔ движения» (уровень 2)
sql
-- проведённые приходы без строк
SELECT r.id FROM receipts r
LEFT JOIN receipt_items ri ON ri.receipt_id = r.id
WHERE r.status = 'posted' AND ri.id IS NULL;

-- проведённые отгрузки без строк списания
SELECT po.id FROM production_orders po
LEFT JOIN production_consumptions pc ON pc.production_order_id = po.id
WHERE po.status = 'posted' AND pc.id IS NULL;
9.6. Компенсация при обнаружении расхождения (уровень 3)
Только компенсирующим движением (adjustment с комментарием), не правкой material_stock руками. Пересчёт material_stock из журналов — аварийная мера, только после фиксации причины:

sql
UPDATE material_stock s
SET quantity = l.qty, updated_at = now()
FROM (SELECT material_id, warehouse_id, SUM(quantity) qty
FROM (
SELECT ri.material_id, r.warehouse_id, ri.quantity
FROM receipt_items ri JOIN receipts r ON r.id = ri.receipt_id
WHERE r.status IN ('posted','reversed')
UNION ALL
SELECT pc.material_id, po.warehouse_id, -pc.quantity
FROM production_consumptions pc JOIN production_orders po ON po.id = pc.production_order_id
WHERE po.status IN ('posted','reversed')
UNION ALL
SELECT ai.material_id, a.warehouse_id, ai.quantity
FROM adjustment_items ai JOIN adjustments a ON a.id = ai.adjustment_id
WHERE a.status = 'posted'
) x GROUP BY material_id, warehouse_id) l
WHERE l.material_id = s.material_id AND l.warehouse_id = s.warehouse_id;
10. Ключевые правила (сводка)
    Одна таблица materials на все материалы. Не создавать отдельные таблицы под щебень/цемент.

Все количества — в базовой единице (кг или т). Приведение через units.factor только на вводе/выводе.

Покупатель, объём и рецепт — в шапке production_orders. Материалы в production_consumptions — производные от рецепта, не вводятся руками.

Списание фиксируется числом в момент проведения: recipe_items.quantity × actual_quantity / recipes.output_quantity. Изменение рецепта потом не влияет на прошлые отгрузки (версионирование valid_from/valid_to).

material_stock — агрегат, обновляется инкрементально (± quantity) в одной транзакции с движением. Читается за O(1) по PK (material_id, warehouse_id).

Журналы — append-only. DELETE запрещён триггером. Отмена проведённого документа — только сторно-документом с отрицательным количеством и ссылкой reversal_of.

DELETE разрешён только для draft (остаток не затронут). Статус reversed — финальный, обратные переходы запрещены.

Проверка остатка при списании — SELECT ... FOR UPDATE + условие quantity − списание ≥ 0 (или разрешённый минус по политике).

Сверка «остаток ↔ журнал» и «документ ↔ движения» — по расписанию. Расхождения чинить компенсирующими движениями, не ручной правкой остатка.

Индексы на журналах: (material_id), (receipt_id) / (production_order_id). При росте объёмов — партиционирование журналов по дате; material_stock от этого не страдает.

11. Схема связей (текстовая)
    text
    units ◄── materials ──► material_categories
    ▲
    │ material_id
    ├── recipe_items ◄── recipes
    │                       ▲
    │                       │ recipe_id
    │              production_orders ──► customers
    │                       │
    │                       │ id
    │              production_consumptions
    │                       │
    │                       ▼
    ├──────────────► material_stock ◄── warehouses
    │                       ▲
    ├── receipt_items ◄── receipts ──► suppliers
    │                       │
    └── adjustment_items ◄── adjustments
    Поток данных:

text
Приход:  receipts + receipt_items  ──(posted)──►  material_stock (+)
Расход:  production_orders + production_consumptions ──(posted)──►  material_stock (−)
Корр.:   adjustments + adjustment_items ──(posted)──►  material_stock (±)
Отмена:  сторно-документ (минус) ──(posted)──►  material_stock (∓)
Сверка:  SUM(журналы)  ⇄  material_stock  (только чтение, для контроля)
12. Что осталось за рамками документа (для следующих итераций)
    Партии/лоты (material_lots) — если нужен учёт по партиям с разной ценой и FIFO.

Себестоимость — средневзвешенная/FIFO через отдельный регистр, если требуется.

Резервирование материалов под заказы (material_reservations) — если нужно блокировать остаток до отгрузки.

Партиционирование журналов по дате при росте до миллионов строк.

Роли и права — кто может создавать/проводить/сторнировать.

reconciliation_log — журнал сверок (когда, что нашли, что сделали) для аудита.

Документ фиксирует структуру и правила на основе обсуждения. Все суммы количеств — в базовой единице; все изменения остатка — только через проведение документов в транзакции; отмена — только сторно; контроль — периодической сверкой журналов с агрегатом.
