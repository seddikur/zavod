Документ: Структура БД учёта материалов завода смесей (АБЗ / РБУ)
1. Назначение и область
   Универсальная система учёта материалов на заводе асфальтобетонных или бетонных смесей: приход от поставщиков, расход по рецептам при отгрузке готовой продукции покупателям, текущие остатки по складам и бункерам. Номенклатура и рецепты различаются пресетом (асфальт / бетон), схема БД одна.

   Примеры материалов: щебень, песок, цемент, битум, минеральный порошок, добавки; для бетона — вода (см. §1.4).

   Ключевой принцип — журнал движений (append-only) является источником истины, таблица остатков — производный агрегат, обновляемый инкрементально в той же транзакции.

   1.1. Принятые архитектурные решения

   Одна таблица materials на все материалы (не отдельная таблица под каждый) — материалы различаются данными, а не структурой.

   Движения хранятся в отдельных таблицах-журналах (приход / расход / корректировка), не удаляются — отмена проведённых приходов и отгрузок только сторно-документом.

   material_stock обновляется инкрементально (± quantity) при проведении документа в одной транзакции. Это паттерн Event Sourcing + Snapshot / CQRS Read Model, в ERP-терминологии — агрегатная таблица остатков (аналог SAP MARD).

   1.2. Целевая СУБД и проект

   В репозитории — MySQL 8.x (utf8mb4, InnoDB). Все примеры SQL в §8–9 приведены к MySQL. Миграции Yii2, транзакции и бизнес-правила дублируются в PHP-сервисах (проведение, сторно, сверка).

   Соответствие типов (ориентир для миграций):

   | В спецификации | MySQL 8 |
   |----------------|---------|
   | bigint PK | BIGINT UNSIGNED AUTO_INCREMENT |
   | numeric(18,6) | DECIMAL(18,2) для количеств / DECIMAL(18,2) для сумм |
   | numeric(18,2) | DECIMAL(18,2) |
   | boolean | TINYINT(1) NOT NULL DEFAULT 1 |
   | timestamptz | DATETIME(6) (UTC в приложении) |
   | date | DATE |
   | text / varchar | TEXT / VARCHAR |

   Upsert остатка: INSERT ... ON DUPLICATE KEY UPDATE (PK material_stock: material_id + warehouse_id).

   Запрет DELETE строк журнала: триггеры BEFORE DELETE на receipt_items, production_consumptions, adjustment_items (§9.3); дополнительно проверка в сервисе при удалении черновиков.

   1.3. Базовая единица количества

   Зафиксирована одна глобальная базовая единица — килограмм (кг). Все quantity в движениях и в material_stock хранятся в кг.

   Конфиг приложения: params['inventory']['baseUnitCode'] = 'kg' (справочник units).

   Единица units и factor на вводе/отображении: пользователь может вводить тонны или м³; перед записью в журнал — пересчёт в кг.

   Выпуск готовой продукции: в шапке production_orders факт (actual_quantity) задаётся в единице рецепта recipes.output_unit_id (т или м³). При проведении отгрузки объём приводится к базе для формулы списания компонентов: сначала actual_quantity пересчитывается в «нормализованный объём выпуска» относительно recipes.output_quantity (в той же единице, что и output рецепта), затем применяется формула §3.2. Количества компонентов в production_consumptions всегда в кг.

   1.4. Вода и пресеты завода

   Вода — обычный material с категорией «Вода»; в рецепте бетона учитывается как строка recipe_items.

   На АБЗ в пресете «асфальт» воду в справочник не заводят или не включают в рецепты — политика пресета и сидера, не отдельная схема.

   Пресет (asphalt / concrete) задаёт начальные категории, материалы и демо-рецепты; структура таблиц не меняется.

   1.5. Склады при списании по отгрузке (принятое правило)

   Списание по каждому материалу идёт со своего склада. Приоритет выбора warehouse_id при проведении production_orders:

   1) recipe_items.warehouse_id (переопределение в рецепте),
   2) иначе materials.default_warehouse_id,
   3) иначе production_orders.default_warehouse_id (запасной склад в шапке заказа).

   В production_consumptions фиксируется итоговый warehouse_id по строке (аудит и сверка). Поле production_orders.default_warehouse_id NOT NULL — обязательный fallback; не заменяет склады по строкам рецепта.

   1.6. Политика отрицательного остатка

   По умолчанию при проведении отгрузки: quantity − списание ≥ 0. Разрешение «в минус» — флаг params['inventory']['allowNegativeStock'] (на этапе 0). При запрете — исключение в сервисе проведения после SELECT ... FOR UPDATE.

8. Методы записи, удаления и смены статуса (MySQL)
   8.1. Приход — создание (draft)
   sql
   START TRANSACTION;

   INSERT INTO receipts (doc_number, doc_date, supplier_id, warehouse_id, status, created_by)
   VALUES ('ПН-001', :date, :supplier, :wh, 'draft', :user_id);
   SET @receipt_id = LAST_INSERT_ID();

   INSERT INTO receipt_items (receipt_id, material_id, quantity, unit_id, price, amount)
   VALUES (@receipt_id, :mat, :qty_kg, :unit, :price, :qty_kg * :price);
   -- остаток НЕ трогаем: документ ещё draft

   COMMIT;

8.2. Приход — проведение (draft → posted)
sql
START TRANSACTION;

SELECT status FROM receipts WHERE id = :receipt_id FOR UPDATE;
-- если status <> 'draft' → SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Invalid status';

INSERT INTO material_stock (material_id, warehouse_id, quantity)
SELECT ri.material_id, r.warehouse_id, ri.quantity
FROM receipt_items ri
INNER JOIN receipts r ON r.id = ri.receipt_id
WHERE ri.receipt_id = :receipt_id
ON DUPLICATE KEY UPDATE
  quantity = material_stock.quantity + VALUES(quantity),
  updated_at = CURRENT_TIMESTAMP(6);

UPDATE receipts SET status = 'posted', posted_at = CURRENT_TIMESTAMP(6) WHERE id = :receipt_id;

COMMIT;

8.3. Отгрузка — проведение (draft → posted)
sql
START TRANSACTION;

SELECT status, recipe_id, actual_quantity, default_warehouse_id
FROM production_orders WHERE id = :order_id FOR UPDATE;
-- если status <> 'draft' → SIGNAL ...

-- 1. строки списания с резолвом склада (§1.5)
INSERT INTO production_consumptions
  (production_order_id, material_id, warehouse_id, recipe_item_id, quantity, unit_id)
SELECT
  po.id,
  ri.material_id,
  COALESCE(ri.warehouse_id, m.default_warehouse_id, po.default_warehouse_id),
  ri.id,
  ri.quantity * (po.actual_quantity / r.output_quantity),
  ri.unit_id
FROM production_orders po
INNER JOIN recipes r ON r.id = po.recipe_id
INNER JOIN recipe_items ri ON ri.recipe_id = r.id
INNER JOIN materials m ON m.id = ri.material_id
WHERE po.id = :order_id;

-- 2–3. для каждой строки pc (сортировка material_id, warehouse_id): FOR UPDATE, проверка, списание
-- SELECT quantity FROM material_stock WHERE material_id = :mat AND warehouse_id = :wh FOR UPDATE;
-- UPDATE material_stock SET quantity = quantity - :consume_qty, updated_at = CURRENT_TIMESTAMP(6) ...

UPDATE production_orders SET status = 'posted', posted_at = CURRENT_TIMESTAMP(6) WHERE id = :order_id;

COMMIT;

8.4. Отмена проведённого прихода — сторно (posted → reversed)
sql
START TRANSACTION;

SELECT status FROM receipts WHERE id = :receipt_id FOR UPDATE;
-- если status <> 'posted' → SIGNAL ...

-- Нумерация: не doc_number || '-СТОРНО' (коллизии UNIQUE), а отдельный номер:
-- CONCAT(:prefix, '-', YEAR(CURRENT_DATE), '-', LPAD(next_seq, 6, '0'))
-- или CONCAT(original.doc_number, '-S', original.id)

INSERT INTO receipts (doc_number, doc_date, supplier_id, warehouse_id, status, reversal_of, reversal_reason, created_by)
SELECT
  CONCAT(doc_number, '-S', id),
  CURRENT_DATE,
  supplier_id,
  warehouse_id,
  'draft',
  id,
  :reason,
  :user_id
FROM receipts WHERE id = :receipt_id;
SET @storno_id = LAST_INSERT_ID();

INSERT INTO receipt_items (receipt_id, material_id, quantity, unit_id, price, amount)
SELECT @storno_id, material_id, -quantity, unit_id, price, -amount
FROM receipt_items WHERE receipt_id = :receipt_id;

-- провести сторно (как 8.2) по @storno_id

UPDATE receipts SET status = 'posted', posted_at = CURRENT_TIMESTAMP(6) WHERE id = @storno_id;
UPDATE receipts SET status = 'reversed', reversed_by = @storno_id WHERE id = :receipt_id;

COMMIT;

Сторно отгрузки — аналогично: production_orders + production_consumptions с минусом; order_number сторно — CONCAT(order_number, '-S', id).

8.5. Удаление
Что	Разрешено?	Как
receipts / production_orders в статусе draft	Да	DELETE (остаток не затронут)
receipts / production_orders в статусе posted	Нет	Только сторно (8.4)
receipt_items / production_consumptions	Нет (триггер)	Только через сторно-документ
adjustments в статусе draft	Да	DELETE
adjustments в статусе posted	Нет	Компенсирующий adjustment (§6.1)
materials, recipes, customers, suppliers	Только is_active = 0	ON DELETE RESTRICT из движений

8.6. Смена статуса — сводная матрица
Документ	Из	В	Условие	Действие с остатком
receipts	draft	posted	есть строки	+ quantity upsert
receipts	posted	reversed	создан сторно	− quantity (через сторно-документ)
production_orders	draft	posted	есть рецепт, расчёт выполнен	− quantity по складам строк
production_orders	posted	reversed	создан сторно	+ quantity (через сторно-документ)
adjustments	draft	posted	есть строки	± quantity upsert
adjustments	posted	—	—	только новый adjustment (компенсация), не reversed

Запрещённые переходы: posted → draft, reversed → posted, reversed → draft. Статус reversed — финальный.

9. Механизмы контроля целостности
   9.1. Транзакционность (уровень 1)
   Движение + UPDATE material_stock — в одном START TRANSACTION ... COMMIT (или Yii::$app->db->transaction). При сбое — ROLLBACK. Для UPDATE остатка проверять ROW_COUNT() = 1 при чистом UPDATE; для upsert — INSERT ... ON DUPLICATE KEY UPDATE.

   9.2. Блокировки (уровень 1)
   При списании — SELECT ... FOR UPDATE по material_stock. Порядок блокировок — сортировка по (material_id, warehouse_id).

   9.3. Запрет DELETE (уровень 1)
   Триггеры BEFORE DELETE на receipt_items, production_consumptions, adjustment_items:

   sql
   DELIMITER //
   CREATE TRIGGER trg_no_delete_receipt_items
   BEFORE DELETE ON receipt_items
   FOR EACH ROW
   BEGIN
     SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Deleting movements is forbidden. Use reversal document.';
   END//
   CREATE TRIGGER trg_no_delete_production_consumptions
   BEFORE DELETE ON production_consumptions
   FOR EACH ROW
   BEGIN
     SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Deleting movements is forbidden. Use reversal document.';
   END//
   CREATE TRIGGER trg_no_delete_adjustment_items
   BEFORE DELETE ON adjustment_items
   FOR EACH ROW
   BEGIN
     SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Deleting movements is forbidden. Use compensating adjustment.';
   END//
   DELIMITER ;

   Отмена проведённых приходов/отгрузок — сторно; проведённых корректировок — компенсирующий adjustment.

   9.4. Сверка «остаток ↔ журнал» (уровень 2)
sql
SELECT s.material_id, s.warehouse_id,
  s.quantity AS stock_qty,
  COALESCE(r.qty, 0) - COALESCE(c.qty, 0) + COALESCE(a.qty, 0) AS ledger_qty,
  s.quantity - (COALESCE(r.qty, 0) - COALESCE(c.qty, 0) + COALESCE(a.qty, 0)) AS diff
FROM material_stock s
LEFT JOIN (
  SELECT ri.material_id, r.warehouse_id, SUM(ri.quantity) AS qty
  FROM receipt_items ri
  INNER JOIN receipts r ON r.id = ri.receipt_id
  WHERE r.status IN ('posted', 'reversed')
  GROUP BY ri.material_id, r.warehouse_id
) r ON r.material_id = s.material_id AND r.warehouse_id = s.warehouse_id
LEFT JOIN (
  SELECT pc.material_id, pc.warehouse_id, SUM(pc.quantity) AS qty
  FROM production_consumptions pc
  INNER JOIN production_orders po ON po.id = pc.production_order_id
  WHERE po.status IN ('posted', 'reversed')
  GROUP BY pc.material_id, pc.warehouse_id
) c ON c.material_id = s.material_id AND c.warehouse_id = s.warehouse_id
LEFT JOIN (
  SELECT ai.material_id, a.warehouse_id, SUM(ai.quantity) AS qty
  FROM adjustment_items ai
  INNER JOIN adjustments a ON a.id = ai.adjustment_id
  WHERE a.status = 'posted'
  GROUP BY ai.material_id, a.warehouse_id
) a ON a.material_id = s.material_id AND a.warehouse_id = s.warehouse_id
HAVING diff <> 0 OR stock_qty IS NULL;

   Учитываем status IN ('posted','reversed') у прихода/отгрузки. Сторно — posted с минусом. Запуск: cron / команда yii.

   9.5. Сверка «документ ↔ движения» (уровень 2)
sql
SELECT r.id FROM receipts r
LEFT JOIN receipt_items ri ON ri.receipt_id = r.id
WHERE r.status = 'posted' AND ri.id IS NULL;

SELECT po.id FROM production_orders po
LEFT JOIN production_consumptions pc ON pc.production_order_id = po.id
WHERE po.status = 'posted' AND pc.id IS NULL;

   9.6. Компенсация при обнаружении расхождения (уровень 3)
   Только компенсирующим adjustment, не правкой material_stock руками. Аварийный пересчёт material_stock из журналов — отдельная консольная команда с жёсткими правами:

sql
UPDATE material_stock s
INNER JOIN (
  SELECT material_id, warehouse_id, SUM(qty) AS qty
  FROM (
    SELECT ri.material_id, r.warehouse_id, ri.quantity AS qty
    FROM receipt_items ri
    INNER JOIN receipts r ON r.id = ri.receipt_id
    WHERE r.status IN ('posted', 'reversed')
    UNION ALL
    SELECT pc.material_id, pc.warehouse_id, -pc.quantity AS qty
    FROM production_consumptions pc
    INNER JOIN production_orders po ON po.id = pc.production_order_id
    WHERE po.status IN ('posted', 'reversed')
    UNION ALL
    SELECT ai.material_id, a.warehouse_id, ai.quantity AS qty
    FROM adjustment_items ai
    INNER JOIN adjustments a ON a.id = ai.adjustment_id
    WHERE a.status = 'posted'
  ) x
  GROUP BY material_id, warehouse_id
) l ON l.material_id = s.material_id AND l.warehouse_id = s.warehouse_id
SET s.quantity = l.qty, s.updated_at = CURRENT_TIMESTAMP(6);

10. Ключевые правила (сводка)
    Одна таблица materials. Склад списания: recipe_items → materials.default_warehouse_id → production_orders.default_warehouse_id.

    Все quantity в журналах и material_stock — в кг; ввод через units.factor; выпуск продукции — в единице recipes.output_unit_id.

    production_consumptions — из рецепта; warehouse_id в строке обязателен после проведения.

    Версии рецептов: один активный is_active = 1 на code — контроль сервисом.

    material_stock — только инкремент в транзакции проведения.

    Журналы append-only; DELETE строк запрещён триггерами.

    created_by → admin_users.id; проведение/сторно — под RBAC (§12, этап 9).

    Сверка и компенсация — §9; отрицательный остаток — §1.6.

11. Схема связей (текстовая)
    text
    units ◄── materials ──► material_categories
              │ default_warehouse_id
              ▼
         warehouses ◄── recipe_items.warehouse_id
              ▲
    recipes ◄─┘
         ▲ recipe_id
    production_orders ──► customers
         │
         ├── production_consumptions (material_id, warehouse_id)
         │
    material_stock (material_id, warehouse_id)

    receipt_items ◄── receipts ──► suppliers
    adjustment_items ◄── adjustments

    Поток данных:

    Приход:  receipts + receipt_items  ──(posted)──►  material_stock (+)
    Расход:  production_orders + production_consumptions ──(posted)──►  material_stock (−)
    Корр.:   adjustments + adjustment_items ──(posted)──►  material_stock (±)
    Отмена:  сторно (минус) ──(posted)──►  material_stock (∓)
    Сверка:  SUM(журналы)  ⇄  material_stock
